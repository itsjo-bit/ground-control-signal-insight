# GCSI Phase 4 — Trust, Safety & Authoritative Execution Boundaries

## Overview

Phase 4 establishes explicit and enforceable trust boundaries between what
a client (frontend, operator, or automated caller) may control and what the
backend asserts as authoritative fact.

The central principle:

> **CLIENTS SUBMIT INTENT.  
> THE BACKEND RECONSTRUCTS FACTS.  
> DETERMINISTIC EVALUATORS AUTHORIZE PHYSICAL CLAIMS.  
> THE HUMAN OPERATOR AUTHORIZES EXECUTION.**

---

## What Clients May Control

Clients may control only:

| Field | Path |
|-------|------|
| Ordered packet IDs (which packets, in which order) | `CandidatePlan.packets[].packet_id` |
| Operator notes (free text) | `ApproveRequest.operator_notes` |
| Plan ID (string key) | `ApproveRequest.plan_id` |

All other fields on submitted `Packet` objects are **ignored** and replaced
by the backend.

---

## What the Backend Is Authoritative For

The backend is the sole authority for:

| Field | Source |
|-------|--------|
| `size_bits` | Authoritative scenario inventory |
| `criticality` | Authoritative scenario inventory |
| `mission_relevance` | Authoritative scenario inventory |
| `deadline_s` | Authoritative scenario inventory |
| `retry_cost` | Authoritative scenario inventory |
| `delivery_requirement` | Authoritative scenario inventory |
| `packet_type` | Authoritative scenario inventory |
| `risk_score` | Deterministic `PlanEvaluator` — never from AI |
| `risk_level` | Deterministic `PlanEvaluator` — never from AI |
| `plan_source` | Backend trust classification — never from client `generated_by` |
| `authoritative_reconstruction` | Always `true` for Phase 4+ approvals |

## Plan Reconstruction

Every API endpoint that accepts a `CandidatePlan` uses
[`plan_integrity.reconstruct_authoritative_plan()`](../backend/app/domain/plan_integrity.py)
to rebuild the plan from the active scenario before any evaluation or simulation.

```
Client CandidatePlan
    └─ [packet_id, packet_id, ...]  ← only the ordering is trusted

reconstruct_authoritative_plan()
    └─ Looks up each packet_id in scenario inventory
    └─ Replaces ALL other packet fields with authoritative values
    └─ Validates: no unknown IDs, no duplicate IDs
    └─ Returns PlanIntegrityTrace with fingerprints

Authoritative CandidatePlan → PlanEvaluator → EvaluationResult
```

## Issued-Plan Registry

When the backend generates plans (via `POST /plans/generate` or
`POST /agent/recommend`), it registers them in the **issued-plan registry**
(`state.issued_plans`).

Each `IssuedPlanRecord` stores:
- `plan_id` — the plan identifier
- `scenario_id` — which scenario was active at generation time
- `canonical_plan` — the authoritative plan as issued
- `packet_order_sha256` — SHA-256 of the ordered packet IDs
- `canonical_plan_sha256` — SHA-256 of the full canonical plan content
- `plan_source` — trusted source classification

### Registry Lifecycle

The registry is **invalidated** (cleared) when:
- A new scenario is loaded
- A state-mutating simulation completes (`POST /simulate`)
- An approval is executed (`POST /approve` or `POST /approve/custom`)

The registry is **NOT cleared** by:
- Read-only operations: `GET /state`, `POST /plans/evaluate`, `POST /plans/what-if`
- Non-mutating what-if simulation: `POST /simulate/what-if`

---

## POST /approve — Standard Approval

The standard approval path enforces issued-plan identity:

1. Look up `plan_id` in the issued-plan registry.  
   → **HTTP 409** if the plan is not registered (was never generated by the backend).

2. Verify the submitted packet order matches the registered order (via SHA-256).  
   → **HTTP 422** if the order differs (tamper detection).

3. Reconstruct all packet facts from the active scenario.

4. Simulate with the authoritative plan.

5. Return `ApproveResponse` containing:
   - `simulation_result` — stochastic simulation outcome
   - `approval_trace` — typed provenance record
   - `executed_plan` — the exact authoritative plan that was simulated

6. Invalidate the issued-plan registry (state has mutated).

### Legacy Path

When `plan` is `None` (only `plan_id` supplied): regenerate plans from
`CandidateGenerator`, look up by `plan_id`, reconstruct authoritatively.
`plan_source = legacy_regenerated`. No issued-plan registry check.

---

## POST /approve/custom — Operator-Custom Plans

Operator-reordered plans (drag-to-reorder) are always accepted without a
registry check, because the operator is intentionally constructing a custom
order.

1. All packet facts are reconstructed from the scenario.
2. Unknown or duplicate packet IDs are rejected (HTTP 422).
3. `plan_source = operator_custom`, `issued_plan_verified = false`.
4. `ApprovalTrace` returned with `issued_plan_verified: false`.

---

## ApprovalTrace

`ApprovalTrace` is a typed provenance record produced for every approval.

```json
{
  "approval_id": "baseline:143022",
  "timestamp_utc": "2024-06-15T14:30:22Z",
  "scenario_id": "mission_v3_nominal",
  "plan_id": "baseline",
  "decision": "approved",
  "plan_source": "deterministic_generated",
  "operator_notes": "verified by flight ops",
  "authoritative_reconstruction": true,
  "issued_plan_verified": true,
  "packet_count": 7,
  "packet_order_sha256": "4f3a...",
  "canonical_plan_sha256": "8b1c..."
}
```

**Note:** SHA-256 fingerprints are *integrity fingerprints*, not
cryptographic signatures. They verify that the plan that was evaluated is
the same plan that was executed within a session. They are not
authentication tokens.

## Risk Score and Risk Level — Always Deterministic

`AIRecommendation.risk_score` and `AIRecommendation.risk_level` are
**always** sourced from the deterministic `PlanEvaluator`, not from AI
self-reporting.

Even when an external LLM (Granite, Gemini, Ollama) produces the
recommendation, the backend rebinds these fields from `EvaluationResult`
before returning the response.

Frontend implementations must display risk values as deterministic backend
outputs, not as AI estimates.

---

## Confidence — Advisory Only

`AIRecommendation.confidence` is the provider's self-reported estimate.
It is advisory and must be presented with an appropriate label:

| `confidence_semantics` value | Meaning |
|------------------------------|---------|
| `uncalibrated_llm` | LLM self-report — not a calibrated probability |
| `heuristic` | Deterministic risk-gap metric (`LocalRuleBasedProvider`) |

**Neither value should be treated as a calibrated probability.**

The `confidence_semantics` field allows the UI to render the appropriate
advisory label without hardcoding provider-specific logic.

---

## Evaluate and Simulate What-If — Non-Mutating

`POST /plans/evaluate`, `POST /plans/what-if`, and `POST /simulate/what-if`
are all **non-mutating**:

- They do not update `state.active_link_state` or `state.active_scenario`.
- They do not invalidate the issued-plan registry.
- They reconstruct packet facts from the scenario before evaluation.

---

## Plan Source Classification

| `plan_source` value | Produced by |
|---------------------|-------------|
| `deterministic_generated` | `POST /plans/generate` |
| `ai_generated` | AI-prioritized plan in `POST /agent/recommend` |
| `operator_custom` | `POST /approve/custom` |
| `legacy_regenerated` | Legacy `/approve` with only `plan_id`, no `plan` object |
| `client_intent` | Generic client submission (e.g. `POST /plans/evaluate`) |

The backend assigns this classification. Client-supplied `generated_by`
strings are never used to determine `plan_source`.

---

## Summary: Trust Boundary Enforcement Points

| Endpoint | Registry check | Packet fact reconstruction | State mutation | Invalidates registry |
|----------|---------------|---------------------------|----------------|----------------------|
| `POST /plans/generate` | — | — (generates from scenario) | No | No |
| `POST /plans/evaluate` | No | Yes (client_intent) | No | No |
| `POST /plans/what-if` | No | Yes (from scenario) | No | No |
| `POST /simulate` | No | Yes (regenerated) | Yes | Yes |
| `POST /simulate/what-if` | No | Yes (client_intent) | No | No |
| `POST /approve` (with plan) | **Yes — 409 if absent** | Yes | Yes | Yes |
| `POST /approve` (legacy) | No | Yes (legacy_regenerated) | Yes | Yes |
| `POST /approve/custom` | No | Yes (operator_custom) | Yes | Yes |
| `POST /agent/recommend` | — | — (generates from scenario) | No | No (registers) |
